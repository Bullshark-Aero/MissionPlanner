BSMP Lights Fix and Separate Release Plan

Status: approved for implementation · Version: v1.0.0 · Created: 2026-09-06 15:20 Europe/London

Exact filename: bsmp-lights-fix-plan--202609061520--v1.0.0--release-and-separation.html

Predecessor: None

Objective

Repair the Judicar 2600 paired-light control, publish the fix through a reviewable Mission Planner pull request, and deliver BSMP and the Judicar aircraft configuration as separate downloads. Every BSMP distribution from this release onward must extract into one version-and-release-date folder.

Known fault

The existing plugin infers the state of DroneCAN-backed outputs 15 and 16 from SERVO_OUTPUT_RAW. Those fields remain zero even when the physical lights work, so the plugin can choose the wrong action and report an unhelpful generic failure. Direct MAV_CMD_DO_SET_SERVO commands to the flight controller are accepted.

Implementation

  1. Build one integrated task branch containing the configuration-bundle feature, the v1.0.3 display and log-sorting fixes, and this repair; target the repository default branch with one pull request that documents the superseded partial PRs.
  2. Remove the invalid telemetry inference. Treat light state as unknown after startup, link loss, or vehicle change. The first action from unknown safely establishes the default ON state; later actions alternate between OFF and ON using the last fully accepted paired command.
  3. Target ArduPilot's flight-controller component explicitly, refuse commands without a live vehicle link, distinguish disconnected, timed-out, rejected, partial, and recovered outcomes, and label displayed state as command state rather than physical feedback.
  4. Add deterministic tests for the state machine, paired-command outcomes, reconnect reset, and target selection. Run the complete existing Windows build and test suite.
  5. Build and sign the revised lights plugin, then produce a new Judicar first-hover .bsampconfig containing that plugin and the existing aircraft-specific configuration. Validate signatures, hashes, manifest ownership, and clean-profile import.
  6. Produce BSMP v1.0.4 as an application-only portable self-extractor. Its archive root must be exactly BSMP 1.0.4 20260906; it must not contain the Judicar .bsampconfig or an installed Judicar plugin.
  7. Add a reusable packaging check so future BSMP releases fail if their root folder does not match BSMP [version] [YYYYMMDD] or if aircraft configuration files enter the application archive.
  8. Inspect both deliverables, test extraction and launch on the shared Windows test VM, commit verified work with the bot identity, push only the task branch, and open the pull request.

Safety and rollback

The command remains a two-output operation with recovery toward the aircraft's default ON state after a partial result. An accepted MAVLink command confirms flight-controller acceptance, not physical lamp state; the UI will say so. Rollback is BSMP v1.0.3 plus the preceding v1.3.0 Judicar bundle. No aircraft parameters or hardware are changed by this work.

Acceptance

Acceptance requires passing source tests and release builds; verified unknown, disconnected, success, failure, and recovery behaviours; a signed and cleanly importable standalone Judicar configuration; an application archive containing exactly one correctly named root folder and no aircraft bundle; successful clean Windows extraction and launch; recorded SHA-256 hashes; a pushed task branch; and an open, unmerged pull request.
